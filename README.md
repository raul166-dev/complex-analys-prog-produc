## 1. Характеристика объекта

| Параметр | Значение |
|---|---|
| **Название** | `auth-service` — модуль аутентификации и авторизации пользователей |
| **Назначение** | Обеспечивает проверку учётных данных пользователей, выдачу, обновление и отзыв JWT-токенов, а также разграничение доступа к защищённым эндпоинтам приложения |
| **Основные функции** | Регистрация и вход пользователя; проверка логина и пароля (`validate_credentials()`); выдача JWT-токена; обновление токена (`/api/v2/auth/refresh`); отзыв токена (`/api/v2/auth/revoke`); хранение сессий в БД |
| **Предполагаемые пользователи** | Разработчики клиентских приложений (потребители API), служба эксплуатации (администраторы), конечные пользователи приложения |
| **Источник и версия** | Внутренний проект команды; ветка `feature/auth-v2`, версия модуля `2.0.0` (согласно `package.json` / `pyproject.toml`). Исходный код доступен в корпоративном репозитории GitHub |

**Границы исследования.** Анализируется только модуль `auth-service` версии 2.0.0 в ветви `feature/auth-v2`: логика проверки учётных данных, компонент JWT-токенов, публичные эндпоинты и миграция схемы сессий. Клиентские приложения, инфраструктура развёртывания и сторонние сервисы (SMTP, внешний identity-provider) в границы исследования не входят.

## 4. Исследование объекта

### 4.1. Анализ документации

Изучены:

- `README.md` репозитория — содержит описание модуля, инструкцию по локальному запуску и перечень эндпоинтов;
- `docs/openapi.yaml` — спецификация API версии 2.0.0;
- `CHANGELOG.md` — история изменений модуля.

**Полученные сведения.** Назначение модуля, перечень эндпоинтов, форматы запросов и ответов, требования к переменным окружения (`JWT_SECRET`, `DB_URL`, `TOKEN_TTL`).

**Чего не хватает.** В README отсутствует раздел о процедуре отката миграции схемы сессий; в OpenAPI-спецификации не описаны коды ответов `429` (rate limiting) и `503` (недоступность БД), хотя соответствующие ветви обработки в коде присутствуют. Это ограничивает проверку критерия 6 и создаёт риск несоответствия документации фактическому поведению.

### 4.2. Анализ структуры проекта

```text
auth-service/
├── auth/
│   ├── __init__.py
│   ├── api.py            # эндпоинты /api/v2/auth/*
│   ├── token_service.py  # выдача, обновление, отзыв токенов
│   ├── credentials.py    # validate_credentials()
│   └── models.py         # модели данных
├── migrations/
│   └── 002_sessions_v2.sql
├── tests/
│   ├── test_api.py
│   ├── test_token_service.py
│   └── test_credentials.py
├── .github/workflows/ci.yml
├── openapi.yaml
└── README.md
```

Структура логична: ответственность разделена по модулям (`api`, `token_service`, `credentials`, `models`), тесты вынесены отдельно, конфигурация CI присутствует. Точка входа — `auth/api.py`, зависимости — веб-фреймворк, драйвер БД и библиотека JWT.

### 4.3. Исследование исходного кода

Изучены `credentials.py`, `token_service.py`, `api.py`, `models.py` и `migrations/002_sessions_v2.sql`. Особое внимание уделено:

- обработке входных данных в `validate_credentials()`;
- проверке срока действия токена в `refresh_token()`;
- логированию в `token_service.py`;
- условиям отзыва токена в `revoke_token()`;
- обратимости миграции `002_sessions_v2.sql`.

### 4.4. Статический анализ

Использованы:

- **ESLint** (для JS-части клиентских утилит) — критических ошибок не выявлено;
- **Bandit** (Python SAST) — обнаружено предупреждение `B105: hardcoded_password_string` в `tests/test_credentials.py` (тестовые данные, не продакшен-секрет) и `B201: flask_debug_true` в `auth/api.py` (см. проблему № 4);
- **TruffleHog** (secret scanning) — секретов в рабочей ветви не обнаружено.

**Ограничение.** Полноценный SAST для всего стека не проводился: часть зависимостей сторонняя, анализатор не покрывает шаблоны SQL-миграций.

### 4.5. Динамический анализ и тестирование

Выполнены сценарии:

| Сценарий | Условия | Ожидаемое поведение | Фактическое поведение |
|---|---|---|---|
| Вход с корректными данными | Валидный логин и пароль | 200, выдан JWT | 200, JWT выдан |
| Вход с пустым паролем | `password=""` | 400 | 400, корректное сообщение |
| Вход с несуществующим пользователем | `login="nouser"` | 401 без раскрытия существования пользователя | 401, сообщение нейтральное |
| Обновление просроченного токена | `exp` в прошлом | 401 | **200, новый токен выдан** (см. проблему № 1) |
| Повторный отзыв уже отозванного токена | Токен отозван дважды | 200 или 409 | 200, идемпотентно — корректно |
| Вход при недоступной БД | Порт БД закрыт | 503 | **500 с трейсбеком в логах** (см. проблему № 5) |

### 4.6. Сравнительный анализ

Сопоставление с требованиями ТЗ (AUTH-42) и с OpenAPI-спецификацией `openapi.yaml`. Расхождение: спецификация не описывает коды `429` и `503`, которые фактически возвращаются модулем.

### 4.7. Анализ изменений (Git)

Изучены `git log --oneline main..feature/auth-v2` и diff ветви:

- 14 коммитов, сообщения в основном осмысленные (`fix(auth): ...`, `feat(auth): ...`);
- **один коммит содержит отладочный `print()` с фрагментом токена** (см. проблему № 3);
- миграция `002_sessions_v2.sql` не содержит `DOWN`-секции (см. проблему № 2).

### 4.8. Анализ потоков данных

Прослежен путь учётных данных:

```text
HTTP-запрос → api.py (валидация формата) → credentials.py (сверка хеша)
→ token_service.py (генерация JWT) → ответ клиенту
```

Токен на пути к клиенту **не логируется** — это корректно. Однако в одном коммите обнаружен `print(token[:10])` (см. проблему № 3), что нарушает принцип.

### 4.9. Ограничения исследования

- Анализ исполняемого файла (дизассемблирование/декомпиляция) **не применялся** — исходный код доступен, необходимости не было.
- Нагрузочное тестирование производительности **не проводилось** — вне границ исследования.
- Полный SAST для SQL-миграций **не выполнялся** — анализатор не покрывает этот тип файлов.
- Среда продакшена **недоступна** — поведение при реальной нагрузке не проверялось.

## 5. Выявленные проблемы

### Проблема № 1. Обновление просроченного токена

- **Что обнаружено:** `refresh_token()` в `token_service.py` (строки 80–95) не проверяет `exp` исходного токена перед выдачей нового. Просроченный токен позволяет бесконечно продлевать сессию.
- **Критерий:** надёжность / безопасность (критерии 3, 4).
- **Подтверждение:** динамическая проверка — запрос с токеном, у которого `exp` в прошлом, вернул `200` и новый токен. Участок кода: `token_service.py:87`.
- **Последствия:** компрометация токена даёт злоумышленнику неограниченный по времени доступ; нарушается требование AUTH-42, п. 3.2.
- **Рекомендация:** добавить проверку `if token.is_expired(): raise TokenExpiredError` перед генерацией нового токена; покрыть негативным тестом.

### Проблема № 2. Необратимая миграция схемы сессий

- **Что обнаружено:** `migrations/002_sessions_v2.sql` содержит только `UP`-секцию, `DOWN`-секции нет.
- **Критерий:** надёжность / управление изменениями (критерии 4, 8).
- **Подтверждение:** просмотр файла миграции; отсутствие скрипта отката в репозитории.
- **Последствия:** при необходимости откатить релиз после применения миграции восстановление старой схемы потребует ручного вмешательства; риск потери данных сессий.
- **Рекомендация:** добавить `DOWN`-миграцию и инструкцию по откату в README; проверить откат на тестовой БД.

### Проблема № 3. Отладочный вывод фрагмента токена в коммите

- **Что обнаружено:** в истории ветви `feature/auth-v2` присутствует коммит с `print(token[:10])` в `token_service.py`. В текущей HEAD-версии строки нет, но она осталась в истории Git.
- **Критерий:** безопасность (критерий 3).
- **Подтверждение:** `git log -p` по `token_service.py`; фрагмент токена виден в diff коммита.
- **Последствия:** при публикации репозитория или передаче истории третьим лицам фрагмент токена может быть использован для атаки; нарушается принцип «токены не логируются».
- **Рекомендация:** переписать историю ветви (`git rebase -i` / `git filter-repo`) до слияния; добавить pre-commit-хук, блокирующий `print` с токенами; включить secret scanning в CI.

### Проблема № 4. Включённый debug-режим в конфигурации API

- **Что обнаружено:** в `auth/api.py` присутствует `app.run(debug=True)` в ветви локального запуска; Bandit отметил это как `B201`.
- **Критерий:** безопасность / надёжность (критерии 3, 4).
- **Подтверждение:** результат Bandit; просмотр `api.py`.
- **Последствия:** при случайном запуске в продакшене debug-режим раскрывает трейсбеки и внутренние данные; возможен доступ к интерактивному отладчику.
- **Рекомендация:** вынести режим в переменную окружения (`DEBUG=false` по умолчанию), добавить проверку конфигурации при старте, исключить ветвь из продакшен-сборки.

### Проблема № 5. Некорректная обработка недоступности БД

- **Что обнаружено:** при недоступной БД модуль возвращает `500` и пишет трейсбек в лог, вместо ожидаемого `503` с нейтральным сообщением.
- **Критерий:** надёжность / обработка ошибок (критерии 2, 4).
- **Подтверждение:** динамическая проверка с закрытым портом БД; в ответе — `500`, в логе — полный трейсбек с путями.
- **Последствия:** клиент не может отличить временную недоступность от ошибки в запросе; раскрытие внутренних путей в логах при недостаточной изоляции логов.
- **Рекомендация:** перехватывать исключения драйвера БД и возвращать `503`; логировать без трейсбека в ответе; добавить тест на недоступность БД.

### Проблема № 6. Неполнота OpenAPI-спецификации

- **Что обнаружено:** в `openapi.yaml` не описаны коды `429` и `503`, фактически возвращаемые модулем.
- **Критерий:** качество документации (критерий 6).
- **Подтверждение:** сопоставление спецификации с фактическим поведением (раздел 4.5) и с кодом `api.py`.
- **Последствия:** клиентские приложения не обрабатывают эти коды; расхождение документации и поведения усложняет интеграцию.
- **Рекомендация:** дополнить `openapi.yaml` кодами `429` и `503` с описанием условий; добавить контрактные тесты на соответствие спецификации.

### Проблема № 7. Недостаточное покрытие негативных сценариев тестами

- **Что обнаружено:** в `tests/` отсутствуют тесты на просроченный токен при обновлении, на недоступность БД и на повторный отзыв токена; покрытие новых строк — 71 % при пороге 80 %.
- **Критерий:** тестируемость и покрытие (критерий 7).
- **Подтверждение:** отчёт о покрытии в CI; анализ состава `test_token_service.py` и `test_api.py`.
- **Последствия:** регрессии в негативных сценариях не отлавливаются автоматически; проблемы № 1 и № 5 не были обнаружены до ревью.
- **Рекомендация:** добавить тесты на перечисленные сценарии; поднять порог покрытия в CI до 80 % для новых строк.

> **Разграничение подтверждённых проблем и рисков.** Проблемы № 1–3, 5, 7 подтверждены динамическими проверками или прямым просмотром кода. Проблема № 4 подтверждена статическим анализатором и просмотром кода, но её фактическое проявление зависит от конфигурации запуска. Проблема № 6 подтверждена сопоставлением спецификации и поведения. Риски, требующие дополнительной проверки: поведение при конкурентных запросах на отзыв одного токена (не проверялось нагрузочно) и корректность SQL-миграции на больших объёмах данных (не проверялось на продакшен-подобной БД).

## 7. Итоговое заключение

Модуль `auth-service` версии 2.0.0 в целом соответствует назначению: основные сценарии входа, выдачи и отзыва токенов работают корректно, структура кода логична, документация покрывает базовые сценарии, история Git в основном осмысленна. Вместе с тем анализ выявил **два критически значимых дефекта** (обновление просроченного токена, отладочный вывод фрагмента токена в истории) и **ряд существенных рисков** (необратимая миграция, некорректная обработка недоступности БД, неполнота спецификации, недостаточное покрытие негативных сценариев тестами). Все выявленные проблемы подтверждены конкретными свидетельствами — результатами динамических проверок, просмотром кода, статическим анализом и сопоставлением с документацией — и не являются предположениями.

До включения изменений в основную ветвь необходимо устранить проблемы критического и высокого приоритета (№ 1, 2, 3, 5), дополнить спецификацию и тесты (№ 6, 7), после чего провести повторное ревьюирование с проверкой результатов автоматических проверок.

### Ограничения исследования

- Анализ исполняемого файла (дизассемблирование/декомпиляция) не применялся — исходный код доступен.
- Нагрузочное тестирование производительности не проводилось — вне границ исследования.
- Полный SAST для SQL-миграций не выполнялся — анализатор не покрывает этот тип файлов.
- Среда продакшена недоступна — поведение при реальной нагрузке и на больших объёмах данных не проверялось.
- Конкурентные запросы на отзыв одного токена не проверялись — требуют отдельного нагрузочного теста.
